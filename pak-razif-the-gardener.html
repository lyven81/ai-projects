Pak Razif The Gardener

Live demoGitHub

By Lee Yih Ven · Published 17 October 2026

Designed for a two-person gardening service in Shah Alam, run by Pak Razif with one helper. While the two work in customers' gardens, customers message about coverage, free site visits and prices, and wait for a reply. The price and the job scope can only be set once Pak Razif has seen the garden.

I built a prototype AI assistant that answers routine enquiries at once and books free site visits into the times Pak Razif has opened. The AI understands each message and answers from approved information. Code checks the postcode, the dates and every booking, and anything that needs Pak Razif reaches the owner's phone inbox as a short summary.

Pak Razif keeps every decision on price, changes and complaints, and decides which visit times are open. In testing, the assistant passed all 33 test conversations on bookings, price requests, handovers and calendar changes. Replay them, or try it live, in the two-phone demo.

One Enquiry, From Message to Booked Visit

Follow one customer message to a routine answer, a booked site visit or a summary for Pak Razif.

  1. The customer asks a question or asks for a free site visit. The AI answers only from approved information and never gives a price or a garden estimate.
  2. Prices, changes, complaints and unusual work go to Pak Razif as an inbox summary. Photos are passed on, never analysed by the AI. Pak Razif calls the customer and sets the price after seeing the garden.
  3. For a visit, code checks the postcode and the dates, and offers only the times Pak Razif has opened. If a day is full, it suggests nearby open days. Same-day requests, dates too far ahead and places outside the area go to Pak Razif.
  4. The customer picks a time and gives their details. Code checks the time and the address again, and books nothing if the time was just taken or the address already has a visit. The booking number is given only after the visit is saved.

What It Does for the Gardening Service

Customers get an answer and a booked visit while Pak Razif works

A visit is booked only into a time Pak Razif has opened, checked again at the moment of saving, and the customer gets a booking reference straight away. Each address holds one upcoming visit at a time.

Prices and decisions stay with Pak Razif

The assistant gives no price, estimate or garden size, and photos reach Pak Razif unchanged, never seen by the AI. Prices, changes, complaints, payments, unusual work and places outside the area reach the inbox with what was asked, what the customer was told and the next step. A visit stays booked until Pak Razif changes it.

Pak Razif runs the calendar from the phone

Pak Razif blocks an open time or opens any blocked one, field work included, and booked visits stay in place. The assistant offers only what is open at that moment. A customer asking whether Pak Razif is on the way gets the duty number once the booking reference and the last four phone digits match a confirmed visit, never a location or an arrival time.

Tools, Resources and Workflow

How Claude works

Claude reads the six resources at the start of each conversation. It calls tools while it needs them and replies when it is done; code checks the reply before it leaves. Limits of 700 output tokens and 8 tool rounds stop a reply from looping.

Code Walkthrough

Dates Are Decided in Code

Bookable dates run from the day after first contact to the same date next month. Today goes to Pak Razif, and Sundays are closed. Each refusal names the next step.

// tools.js: checkDate
    // Date checks shared by find_open_slots and book_site_visit.
    function checkDate(state, date) {
      if (!isIsoDate(date)) return fail("invalid_input", "Date must be YYYY-MM-DD.", true);
      const w = windowFor();
      if (date < today()) return fail("past_date", `That date has passed. Today is ${dateText(today())}.`, true);
      if (date === today()) return fail("same_day", "Same-day visits need Pak Razif's go-ahead (W9). Do not book; forward with hand_to_pak_razif, reason time_not_bookable, and reply with R11.", false);
      if (date > w.to) return fail("beyond_window", `Visits can be booked up to ${dateText(w.to)}, the same date next month from first contact (W8). Do not book; forward with hand_to_pak_razif, reason time_not_bookable.`, false);
      const day = state.days[date];
      if (!day) return fail("beyond_window", "That date is not in Pak Razif's calendar yet. Forward with hand_to_pak_razif, reason time_not_bookable.", false);
      if (day.closed) return fail("closed_day", `${dateText(date)} is closed (${day.closed}; W1, W2). Offer the nearest open day.`, true);
      return null;
    }

Photos Are Forwarded, Never Seen

Only photos attached in this conversation can be forwarded, each once. The model passes IDs; the image goes straight to Pak Razif's inbox.

// tools.js: forward_photo
      forward_photo({ photo_ids, note }, ctx) {
        const state = store.load();
        const asked = (Array.isArray(photo_ids) ? photo_ids : [photo_ids]).map((x) => str(x).toUpperCase());
        const ids = asked.filter((id) => session.uploads.includes(id) && (state.uploads || []).some((u) => u.id === id && !u.forwarded));
        if (!ids.length) return fail("no_photo", "No photo from this conversation matches those IDs, or it was already forwarded. Only photos the customer attached here can be forwarded. Do not say a photo was passed on.", false);
        state.uploads.forEach((u) => { if (ids.includes(u.id)) u.forwarded = true; });
        const ref = session.own[session.own.length - 1] || "";
        const item = newItem(state, {
          kind: "photos", category: "photos", photos: ids, images: ids.map((id) => state.uploads.find((u) => u.id === id).image),
          note: str(note), booking_ref: ref, customer: { name: contactOf(ctx).name, phone: contactOf(ctx).phone },
          customer_words: customerWords(ctx), contact: contactOf(ctx),
        });

        store.save(state);
        session.photoItems.push(item);

A Handover Pak Razif Can Act On

He cannot see the chat, so every summary field is required. Code adds the customer's own words, name, phone, photos and the time.

// tools.js: hand_to_pak_razif
      hand_to_pak_razif(input, ctx) {
        const reason = str(input.reason);
        if (!HANDOVER_REASONS[reason]) return fail("missing_fields", "reason must be one of: " + REASON_IDS.join(", "), true);
        const asked = str(input.what_was_asked), told = str(input.told_customer), next = str(input.recommended_next_step);
        const missing = [["what_was_asked", asked], ["told_customer", told], ["recommended_next_step", next]].filter(([, v]) => v.length < 8).map(([k]) => k);
        if (missing.length) return fail("missing_fields", `Pak Razif cannot see this chat. Fill in: ${missing.join(", ")}, one line each (P32).`, true);
        const state = store.load();
        const c = contactOf(ctx);
        const photos = state.inbox.filter((i) => session.photoItems.includes(i.id)).flatMap((i) => i.photos);
        const id = newItem(state, {
          kind: "handover", category: reason, reason, reason_label: HANDOVER_REASONS[reason].label, rules: HANDOVER_REASONS[reason].rules,
          customer: { name: c.name, phone: c.phone }, customer_words: customerWords(ctx),
          address: str(input.address), what_was_asked: asked, preferred_time: str(input.preferred_time),
          told_customer: told, recommended_next_step: next, photos, contact: c,
        });
        store.save(state);
        return { ok: true, inbox_item: id, rules: HANDOVER_REASONS[reason].rules.concat(["P33"]),
          message: "Passed to Pak Razif. Tell the customer it has been passed on and that he will get back to them. Do not promise when." };
      },

The Duty Number Only After a Match

The reference and the last 4 phone digits must match a confirmed visit from today on. Nothing else about the booking is returned.

// tools.js: eta_contact_check
      eta_contact_check({ booking_ref, phone_last4 }) {
        const last4 = str(phone_last4);
        if (!/^\d{4}$/.test(last4)) return fail("invalid_input", "phone_last4 must be exactly 4 digits. Ask the customer.", true);
        const state = store.load();
        const ref = normRef(booking_ref);
        const b = state.bookings.find((x) => x.ref === ref);
        if (!b || b.status !== "confirmed" || b.date < today() || digits(b.phone).slice(-4) !== last4)
          return fail("no_match", "Those details do not match an upcoming visit. Reply with R12. Do not give the duty number or any booking detail.", true);
        return { ok: true, duty_number: state.duty_number, rules: ["P15", "P18"],
          message: "Give the customer this number to call for the latest update. Give no arrival time, location or reason for a delay (P17)." };
      },
    };

His Calendar, His Call

Pak Razif's page has two actions: Done, and tapping a slot. He can block an open slot or open any blocked one; booked visits stay.

// tools.js: OWNER
  const OWNER = {
    // Done (Seen for a new visit): the item moves to the closed list.
    done(state, id, now) {
      const i = state.inbox.find((x) => x.id === id);
      if (!i || i.status !== "open") return fail("not_open", "No open inbox item with that ID.", false);
      i.status = "done"; i.closed_at = now || DEFAULT_NOW;
      return { ok: true };
    },
    // Tap an open slot to block it; tap any blocked slot, field work included, to open it
    // (P38, W10): his calendar is his to run. Booked slots hold a customer and are not changed here.
    toggleSlot(state, date, slot) {
      const day = state.days[date];
      const cell = day && day.slots[slot];
      if (!cell) return fail("no_slot", "No such slot.", false);
      if (cell.status === "open") { day.slots[slot] = { status: "blocked", reason: "Blocked by Pak Razif" }; return { ok: true, status: "blocked" }; }
      if (cell.status === "blocked") { day.slots[slot] = { status: "open" }; return { ok: true, status: "open" }; }
      return fail("not_changeable", "A booked visit is changed with the customer, not here.", false);
    },
  };

A Reply Is Checked Before It Leaves

A reply that claims a booking or a forwarding is compared with the tools that ran in that turn. If none did it, the reply goes back once, then a safe fallback is sent.

// agent.js: claimProblem
  const FORWARD_CLAIM = /\b(I('ve| have)|has been|have been|was|were)\s+(\w+\s+){0,5}?(passed|forwarded|sent|handed)\b[^.?!]{0,60}\b(Pak Razif|him)\b/i;
  // "Your site visit is confirmed", "is booked for", "Your booking reference is".
  const BOOKING_CLAIM = /\b(visit|it|appointment)\s+(is|has been)\s+(now\s+)?(confirmed|booked)\b|\bbooking reference is\b/i;
  const CLOSES_CHAT = /I'll end the chat here/;

  function claimProblem(reply, calls) {
    const ok = (name) => calls.some((c) => c.name === name && c.result && c.result.ok);
    if (FORWARD_CLAIM.test(reply) && !ok("hand_to_pak_razif") && !ok("forward_photo"))
      return "Your reply says something was passed to Pak Razif, but neither hand_to_pak_razif nor forward_photo succeeded in this turn. If it should go to him, call the tool now; otherwise rewrite the reply without that claim.";
    if (BOOKING_CLAIM.test(reply) && !ok("book_site_visit"))
      return "Your reply says a visit is booked or confirmed, but book_site_visit did not succeed in this turn. Rewrite the reply without that claim.";
    return null;
  }

When It Passes an Enquiry On

The prompt names nine fixed reasons and says to pass an enquiry on at once. The tool then holds it to that list.

// prompt.js: pass it to Pak Razif
PASS IT TO PAK RAZIF (hand_to_pak_razif)
Pak Razif cannot see this chat and replies to the customer himself by phone or WhatsApp. Fill every field so he can act on the item alone: what_was_asked, told_customer, recommended_next_step (one line each), plus the address and preferred day or time if the customer gave them. Code adds the customer's words, name, phone and any photos.
Reasons:
- price_request: any price, transport charge, tax or discount (P23).
- unusual_work: work not among the general services in P5, or unclear requirements (P24). Do not say whether he will take it.
- outside_area: a nearby postcode outside the coverage (P25, A4). Reply with R5.
- outstation: another state, e.g. Melaka, Penang, Johor (P26, A5). Do not promise acceptance.
- time_not_bookable: a visit today (R11), a date beyond the booking window, or when no open slot suits and the customer wants another time (P27).
- change_or_cancel: change of date or time (R10), cancellation (R7), address correction (P28). The visit stays booked until he changes it.
- after_visit: the work date or arrangements after a site visit (P29, Q5).
- complaint_or_payment: complaints, damage, compensation, payments and refunds (P30, P35, P21). For a complaint with no account yet, reply with R8 and ask what happened; pass it on once they describe it.
- asks_for_him_or_unclear: the customer asks to speak to Pak Razif, or a business question the resources do not cover (P31).
Pass it on at once with what the customer has given; do not ask for a booking reference or other details first. Pak Razif has the customer's name and phone from the chat and finds the booking himself.
After a successful handover, say it was passed to Pak Razif and he will get back to them. Never promise when.
Not passed on: questions unrelated to gardening or site visits (P37, decline politely), requests to measure land, and ETA questions (the check tool answers those).
