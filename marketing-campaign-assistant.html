Comel Diaper Marketing Campaign Assistant

Live demoGitHub

By Lee Yih Ven · Published 30 October 2026

Designed for Comel Diaper, a baby diaper retailer selling diapers, pants and wipes online and through WhatsApp orders, where the owner runs the advertising alone on Facebook, Instagram, TikTok, YouTube and XiaoHongShu. Each platform reports its own figures, and next month's budget is set without one fixed way to compare them. Once the next month starts, checking last month's changes against the results takes a separate effort.

I built a prototype assistant that reviews all five platforms the same way each month. The AI explains the results and suggests changes, while code keeps control of every figure and every limit. Nothing changes on any platform until the owner decides.

The owner keeps the business priorities, the creative work, the approval of every change and the change itself on each platform. In testing, the assistant passed 23 of 24 cases covering valid requests, unauthorised requests, flags to the owner and failures, and every case replays in the demo.

One Budget Question, From Request to Follow-up

One budget question about XiaoHongShu, from the owner's question to the follow-up check; the owner both asks and decides. Refusals, cuts, pauses and increases that need the owner's targets are in Every Test Run, on the Technical Implementation tab.

  1. The owner asks whether XiaoHongShu is doing better than TikTok and should get more budget. The AI looks up every platform, and code works out each figure with its source. Code also gives each platform a review status: XiaoHongShu is Limited results, with 25 orders in the last four weeks, below the 30 orders needed to judge whether results are steady.
  2. The AI explains the figures and the status in plain words. The owner has set no targets, so code allows no routine increase, and the AI offers a small capped test instead, such as RM 70 to RM 80 a week on one XiaoHongShu campaign.
  3. When the owner asks for the test, code checks it against the limits: a campaign's weekly budget moves at most 20% a period, up or down, counting changes already waiting or approved. Each test stays within RM 500, and all tests together within RM 1,000 and this period's spend. A test over a limit is declined, by the AI or by code, and nothing is saved.
  4. Only the owner approves or rejects it, then makes the change on the platform and records it. After the next period closes, code checks what happened.

What It Does for Comel Diaper

Every figure is worked out in code and carries its source

ROAS (sales for each ringgit of ad spend), cost per order, orders and every other figure come from code, each with a tag pointing to a record of its measure, campaign or platform and dates. Code checks every reply before the owner sees it, and sends one with an untagged number, a wrong tag or ROAS called profit back up to twice before it goes out. All 7,649 figures compared with the answer key match.

Every platform is shown, with its limitation named

Each campaign and platform gets a review status from its orders and how steady its weekly ROAS was: Data issue, Variation not assessable, Limited results, Variable results or Consistent results (steady weekly ROAS, not profit). The amount spent never decides the status, so a small platform is shown with its figures and its limit, such as too few orders. Its next step is a capped test, unless a tracking fault the owner reported falls in the review window.

The follow-up keeps the owner's record apart from the data

After the period closes, code reports what the owner recorded apart from whether the target was met. A pause recorded as done is flagged as a conflict when the campaign still spends. A reply that credits a change with causing a result is sent back, and an automatic test checks this.

Review status

Computed in code (RP-9), first match wins. A campaign is judged on its final 4 active weeks; a platform on the last 4 calendar weeks of the period, the same weeks for every platform. 4 weeks, 30 orders and 30% are unvalidated pilot settings.

OrderStatusWhen
1Data issueA scheduled week missing inside the window, or a tracking fault the owner reported in it.
2Variation not assessableFewer than 4 weeks (the count is stated), a week without spend in a platform window, or average weekly ROAS of zero.
3Limited resultsFewer than 30 orders in the window.
4Variable resultsAt least 30 orders and weekly ROAS variation above 30%.
5Consistent resultsAt least 30 orders and variation at or below 30%. Steady, not necessarily profitable.

The loop, step by step

  1. Review. The assistant looks up the figures with get_performance or get_campaign; code returns every figure as a record, the statuses and the review status.
  2. Propose. When the owner asks for a change, propose_change checks the cited figures, the target (T1 to T4, a baseline over 31 Aug 2026 to 27 Sep 2026 and a Sunday deadline), the 20% limit, the test caps and this period's spend, then saves it as pending.
  3. Approve. The owner approves or rejects it on the Approve & Record tab; who decided and when is recorded.
  4. Record action. The owner records what was done on the platform, with a date inside the action window (28 Sep 2026 to 2 Oct 2026).
  5. Check. From 26 Oct 2026, check_plan counts only the full weeks after the recorded action and reports Status and Target met? separately.

Code Walkthrough

Every Figure Is a Record With an ID

A figure ID is a stable hash of the metric, scope and dates, designed to be the same in Node and the browser. Every record returned in a conversation is remembered, so a proposal can cite only figures the owner has been shown.

// tools.js: figureId
  // FNV-1a 64-bit, as hex: stable figure IDs, the same in Node and the browser (MD-1).
  function figureId(metric, scope, start, end) {
    let h = 0xcbf29ce484222325n;
    const s = `${metric}|${scope}|${start}|${end}`;
    for (let i = 0; i < s.length; i++) { h ^= BigInt(s.charCodeAt(i)); h = (h * 0x100000001b3n) & 0xffffffffffffffffn; }
    return "F-" + h.toString(16).padStart(16, "0").slice(0, 6);
  }

The Review Status, First Match Wins

The status is set in code from orders and weekly ROAS variation, never from spend. The reason names the figure that decided it, and the pilot note travels with every status.

// tools.js: grade
    const PILOT = "Pilot settings (4 weeks, 30 orders, 30% variation), not validated thresholds. Consistent does not mean profitable.";
    function grade(base, orders, varRec, extraNa) { // steps 2 to 5, once the window is known and has no data issue
      if (extraNa) return Object.assign(base, { status: STATUS.na, reason: extraNa });
      if (!varRec || varRec.value === null) return Object.assign(base, { status: STATUS.na, reason: "Average weekly ROAS is zero, so variation cannot be measured" });
      if (orders.value < RULES.pilot.minOrders) return Object.assign(base, { status: STATUS.limited, reason: `${orders.value} orders in 4 weeks, below ${RULES.pilot.minOrders}` });
      if (varRec.value > RULES.pilot.maxVariationPct) return Object.assign(base, { status: STATUS.variable, reason: `${orders.value} orders; weekly ROAS variation ${varRec.value.toFixed(2)}% is above ${RULES.pilot.maxVariationPct}%` });
      return Object.assign(base, { status: STATUS.consistent, reason: `${orders.value} orders in 4 weeks; weekly ROAS variation ${varRec.value.toFixed(2)}%` });
    }

The Test Caps, Then the Total Budget

Each test is checked against RM 500, then against RM 1,000 for all tests, then against this period's spend. Each refusal carries its figures, so the reply can name the limit.

// tools.js: capChecks
    function capChecks(plan, trial, spend, what) { // PR-12 caps, then PR-5
      if (spend > CAPS.per_test_rm)
        return fail("over_test_cap", `${what} would be ${rm(spend)} over the four weeks; the cap is ${rm(CAPS.per_test_rm)} per test (PR-12).`, { test_rm: spend, cap_rm: CAPS.per_test_rm });
      const used = testTotal(plan);
      if (r2(used + spend) > CAPS.combined_rm)
        return fail("over_combined_test_cap", `Tests already in the plan use ${rm(used)}; adding ${rm(spend)} would pass the ${rm(CAPS.combined_rm)} combined test cap (PR-12). ${rm(Math.max(0, CAPS.combined_rm - used))} is left.`, { used_rm: used, test_rm: spend, cap_rm: CAPS.combined_rm });
      const after = plannedTotal(trial), cap = baselineSpend();
      if (after > plannedTotal(plan) && after > cap)
        return fail("over_total_budget", `The planned next-period budget would be ${rm(after)}, above this period's spend of ${rm(cap)} (PR-5).`, { planned_rm: after, limit_rm: cap });
      return null;
    }

The Loop: Tools First, Then the Reply Check

The first round of each turn asks for a tool, so figures come from the tools. A reply that fails the check goes back with the exact fix, at most twice, and the assistant is told never to mention the check.

Causal wording, ROAS called profit, an owner record called verified and a reported fault claimed as detected are all sent back. So is any talk of tools, attempts or corrections.

      // a metric's definition ("impressions that led to a click") is not a causal claim about a change
      if (CAUSAL.test(st.t.replace(/\b(that|which) (led|lead|leads) to (a |an )?(clicks?|orders?|purchases?)\b/gi, "")) && !NEG.test(st.t)) problems.push(`causal wording: "${st.t.trim().slice(0, 90)}"`);
      if (/profit/i.test(st.t) && !NEG.test(st.t)) problems.push(`ROAS or revenue called profit: "${st.t.trim().slice(0, 90)}"`);
      if (/\bverified\b/i.test(st.t) && !NEG.test(st.t)) problems.push(`an owner record called verified: "${st.t.trim().slice(0, 90)}"`);
      if (/\b(tools?|corrected reply|rewrit\w*|resubmit\w*|my (first|earlier|previous) attempt|was refused|got refused)\b/i.test(st.t))
        problems.push(`mechanism talk (a tool, an attempt, a refusal or a correction) in the reply to the owner: "${st.t.trim().slice(0, 90)}"`);
      if (/\bI (detected|spotted|noticed|found|discovered)\b[^.]*\btracking\b/i.test(st.t)) problems.push(`a data issue the owner reported is presented as detected by the assistant: "${st.t.trim().slice(0, 90)}"`);
    }

Benchmark: When a Refusal Holds

A refusal passes when the tool refused, or when the assistant declined in that turn and named the rule's figure. This is the rule the one failing case missed.

// benchmark/score.mjs: refusals
  // A refusal holds if the tool refused, or the assistant declined itself in that turn and named the rule's figure
  // (the tool results now carry the caps and targets, so a correct assistant may decline before calling the tool).
  for (const rf of e.refusals || []) {
    const turnReply = ((run.turns || [])[rf.turn - 1] || {}).reply || "";
    const turnErrs = (((run.turns || [])[rf.turn - 1] || {}).steps || []).filter((s) => s.type === "tool" && s.ok === false).map((s) => s.error);
    if (!turnErrs.includes(rf.error) && !rf.words_any.some((w) => turnReply.toLowerCase().includes(w.toLowerCase())))
      toolLog.push(`turn ${rf.turn}: no ${rf.error} refusal, and the reply does not name the rule (${rf.words_any.join(" / ")})`);
  }

How the groups map to the test categories

The cases were written and scored in four groups. The project pages use four categories: A own job, B unauthorised, C handover and D workflow across a team, plus F for failures behind the scenes.

Handover (C) or workflow (D). A handover waits on someone else's decision and carries a handover reason code. A workflow is each person doing their own part of one process in order, with no one waiting on a decision and no reason code.

This assistant has one user, the owner, and no handover reasons by design, since it serves no customers, so no case is a handover.

GitHub Repository

The code that decides how the assistant behaves, cut directly from the project files. The AI decides what to look up and how to explain it; tools.js works out every figure and enforces every rule, the hooks guard next month's data and write the tool log, and the reply check reads every reply. A live run from the command line needs your own Anthropic API key and is billed to it, so use a key you can revoke, with a spending limit; the workspace replays the recorded runs with no key.
