# Polyclinic Sivakumar Clinic Desk

One Claude agent (Haiku 5.5, `claude-haiku-5-5`) serving the three people of a one-doctor GP clinic: Siti Kasim (FD-01, clinic assistant), Dr Sivakumar a/l Ramachandran (GP-01, general practitioner and owner) and Ms Yong (PH-01, pharmacist). Each person signs in to their own copy of the tools, listing only their own actions, and their own prompt, describing only their own job (founder, 28 Oct). The agent only chooses which of the person's tools to call. One shared PreToolUse hook decides before every tool runs, one shared PostToolUse hook converts and filters every result, and the back end repeats the critical checks. Work moves between the three people as tasks and notices written in code, never agent to agent. The five approved policy files in `sources/` are the source; where anything else disagrees, they win. The plan and the founder's decisions are in `../../_plan/`.

## Layout
- `sources/*.txt`: the five approved policies (35 clauses): Hours and Services (PS-HS), Price List (PS-PL), Panel Price Schedule (PS-PN), After the Consultation (PS-AC), Roles and Privacy (PS-RP). Change a clause, a price or a dose here, nowhere else.
- `build_policies.py` -> `resources/`: one `.md` per policy (the MCP resources `clinic://hours-and-services`, `reference://price-list`, `policy://panel`, `policy://after-consultation`, `policy://roles-and-privacy`), `clauses.json` and `policy_tables.json` (staff, hours, holidays, services, the 12-medicine formulary with drug classes and dose ranges, the allergy mapping, Panel Teratai and Panel Cempaka with their valid periods, the handover and query reasons, the resource list, the document serial prefixes). Every table is parsed from the policy text. Also writes `policies.html`, the page people read.
- `generate_data.py` (seed 42) -> `data/*.json`: 110 patients with history, then today's records at the test calendar, Tuesday 2 June 2026, 10:00 Malaysia time (`data/meta.json`): the queue, this morning's consultations, checks, dispensing, bills, payments, tasks, stock and yesterday's reconcile, each planted for a case in the Answer Key. `meta.who` maps each case key to its patient.
- `lib/format.js`: the one result shape `{ tool, status, data, error, next_step }` (status `ok`, `refused` or `error`; `next_step` is `{ text, person, say, basis }`, `say` the reply written in code, `basis` the Basis line), the error codes with their default clauses, and the conversions (sen to RM, Unix seconds to Malaysia time).
- `lib/rules.js`: tools offered per role (`TOOLS_FOR`) and actions per role (`ACTIONS`), staff lookup, the medicine and service lookup, the pharmacist's four checks (complete, allergy by drug class, dose within the formulary range, stock), prices and the panel split, clinic days and 15-minute slots, and every sentence written in code (`say.sent`, `say.noAuthority`, `say.noAccess`, `say.noGpRecord`, `handoverNotice`, `answerNotice`).
- `lib/backend.js`: the data layer. Repeats the role check for every action and runs the record checks (identification, workflow order, the four checks, prices, payment equal to the patient's share, one payment per bill, documents copied exactly from the GP's record). Creates tasks and notices. `checkAndDispense` runs the four checks and either dispenses or holds the prescription and raises the query itself; `queryGp` sets the reason from the check (P4 when it passes); `handOver` sets the reason and the receiver from the matter and the stage of the visit. Refusals are thrown as `{ backend: true, code, message, data }`. Fault injection for the benchmark through `opts.faults`.
- `hooks/pre_tool_use.js`: the signed-in staff ID, the tool and the action offered to the role, case notes and the medicines view by role, the handover matter (a reason passed by the model is dropped: code sets it), and patient identification given. A block comes back in the shared shape, with the reply written in code for a refusal about who is asking.
- `hooks/post_tool_use.js`: converts money and times, filters the fields by role, writes the Basis line and, for a fixed outcome (a handover sent, an answer recorded, no access, no authority), `next_step.say`.
- `tools.js`: the seven tools (`patient`, `schedule`, `record_consultation`, `dispense`, `billing`, `documents`, `tasks`), each an intro, one line per action and its properties; `toolsFor` builds each person's copy (front desk 5, GP 5, pharmacist 3) with only that person's actions, their descriptions and the properties they use. Patient views stay listed for everyone so a refused view gets the code-written no-access reply. `createDesk` (every call runs PreToolUse, the back end, PostToolUse, and is logged) and `memoryStore`. Loaded by the MCP server, the tests, the benchmark and the pages.
- `mcp_server.mjs`, `.mcp.json`: stdio server `polyclinic-sivakumar-desk`, 5 resources and 7 tools. The staff ID arrives in the request's `_meta.staff`, never from a tool argument. Tools and resources are listed by role; the pharmacist is neither listed nor served the Price List or the Panel Price Schedule. The hook record goes back in the result's `_meta`. Env: `PS_STATE` (data folder, default `./data`, written through on every change), `PS_NOW` (Unix seconds, default `meta.now`), `PS_FAULTS` (JSON).
- `prompt.js`: `buildSystem(resources, session)`: the policies the signed-in person may read (with a cache marker), that person's job only, the shared working and reply rules, one worked example per reply level for that person, and that person's latest notices.
- `agent.js`: `runTurn`, the loop on Haiku 5.5: `tool_choice` "any" in the first round with an "auto" fallback (counted), a plain-text ending with no tool call sent back once, 900 output tokens per call, 8 tool rounds. `next_step.say` is shown as it is with no further model call; `replyFixes` checks every other reply (the signed-in person named by full or short name, pronouns, length, opening, "pending") and sends it back at most twice; code adds the Basis line.
- Pages (build outputs from `build_desk_preview.mjs`): `desk-preview.template.html` -> `desk-preview.html` (working preview on `benchmark/sample.json`); plus `desk-layout1.overrides.js` -> `desk-layout1.html` (Layout 1, side by side); plus `desk.prod.js`, `agent.js`, `prompt.js` and `benchmark/results.json` -> `clinic-desk.html`, the published clinic desk (Replay of the full recorded run with its scores, Live with the visitor's own API key). Each inlines the shared modules, the data, the tables and the Answer Key, so it runs the same tools and hooks with no server.
- `benchmark/`:
  - `build_cases.py` -> `cases.json` and `Answer Key.html`: 20 use cases in four categories (A1 to A6 own job, B1 to B4 unauthorised, C1 to C6 handover loop, D1 to D4 workflow across the team) plus F1 to F4 failure runs. Each A, B and C question is sent by its right person, each B question also by the person who may do it (B1-GP, B3-FD, B4-FD): 19 runs. D runs once with each step as its right person, F once each: 27 runs, 49 scored steps. C6 sends the same patient question before the consultation (to the GP) and after dispensing (to the pharmacist). Run IDs read `A1-FD`, `B3-PH`, `D1`, `F2`.
  - `harness.js`: loads the data, builds a case's starting state without a model, the canonical tool calls per expected result, the scoring (right tool, right action, right result, the data check) and the ten hard limits. Never the reply wording. A request outside the person's tools passes only with reads of the person's own records, no refusal and no action outside the person's list (the 27 Oct tolerance for a refused attempt is removed).
  - `test_tools.js` (176 checks) and `test_mcp.mjs` (15 checks): no key, no model.
  - `run_benchmark.js`: every step starts a fresh MCP server on a copy of the run's data, the staff ID in `_meta`. Writes `<out>.json` (full transcripts and hook records) and `<out>.md`; per-run data in `runs/` (git-ignored).
  - `build_sample_page.py` -> `Sample Questions.html`: one question per category from `sample.json`.
  - `results.json`, `results.md`: the final run (28 Oct), 27 of 27, 49 of 49 steps, 0 hard-limit breaches, 0 calls outside a person's own actions. `results.*.bak-2026-10-28-roles`: the 52-run result before per-person tools. `rerun-b1.*`: the B1-FD rerun. `sample.json`, `sample.md`: the 4-case sample (B3-PH, C1-PH, C6-FD, D1).
- `_old/`: the earlier Klinik Dr Fang files, kept in the run folder for reference and not published. Not loaded by anything.

## Rules that must hold
- **Staff ID from the session only.** The signed-in staff ID comes from the request `_meta` (`_meta.staff`), never from the model or a tool argument. A staff ID typed into the arguments changes nothing.
- **Tools and actions offered by role** (PS-RP-01, `lib/rules.js`): each person's tool list carries only these actions (`toolsFor`), and PreToolUse and the back end refuse any other:

| Tool | Siti Kasim (desk) | Dr Sivakumar (GP) | Ms Yong (pharmacist) |
|---|---|---|---|
| `patient` | find, register, update_contact | find | find |
| `schedule` | book, change, cancel, check_in, view_queue | view_queue, call_next | not offered |
| `record_consultation` | not offered | record, amend_prescription | not offered |
| `dispense` | not offered | not offered | check_and_dispense, query_gp, view_stock |
| `billing` | prepare_bill, record_payment, reconcile_day, view_bill, view_payments | view_bill, view_payments, view_owner_review, view_panel_bills, acknowledge_panel_bill | not offered |
| `documents` | prepare, mark_issued, list | not offered | not offered |
| `tasks` | list, hand_over | list, answer | list, answer (D5 only) |

- **Workflow order**, enforced in the back end: a consultation is recorded only for the patient with the GP now; check and dispense only after a recorded consultation with a prescription; dispense only after a passed check on the current prescription (or the GP's answer to keep it) and with no open query, a failed check holding the prescription and raising the query in code; bill after dispensing when there is a prescription; a panel bill only after the patient's ID is verified and inside the panel's valid period; payment equal to the patient's share, one payment per bill; issue only after prepare.
- **Only the GP changes a prescription** (`record_consultation amend_prescription`). A query carries one reason, set by code: P1 allergy conflict, P2 dose or unclear prescription, P3 out of stock from a failed check (raised by `check_and_dispense` itself), P4 another concern when Ms Yong queries with the checks passing. The prescription is held until the GP amends it or answers to keep it. A keep overrides only a clinical judgement (an allergy, a dose outside the range); when a medicine is out of stock or a line is incomplete, the keep is refused (`keep_not_possible`, reply written in code: amend instead) and check-and-dispense refuses it again as the backstop. An amendment replaces the old check and creates a new check task.
- **Who sees what** (PS-RP-02 to PS-RP-04), in PreToolUse, the back end and the PostToolUse field filter: case notes reach the GP only; the pharmacist sees allergies, conditions, current medicines and the prescription, and nothing about panels, prices or bills (nor the Price List and Panel Price Schedule resources); the desk sees contact, panel and allergy flags, and no prescription detail beyond the bill lines.
- **MCs and referral letters** are prepared only from the GP's consultation record, copied exactly, one serial number each, ready for the GP's signature. Neither is raised after the consultation: there is no other path to one, and a request with no record gets the code-written `no_gp_record` reply.
- **Desk handovers** (`tasks hand_over`) carry a patient's own question or concern to a colleague in the clinic. Never staff work. Siti gives the question and a matter (`question`, `unwell`, `outside_policy`); code sets the reason and the receiver from the stage of the visit (Siti, Dr Sivakumar, Ms Yong, Siti): a question before the consultation, D1 to the GP; after the medicine is dispensed, D5 to the pharmacist; `outside_policy` before the consultation, D4 to the GP; `unwell`, D2 to the GP at any time. While a prescription is with Ms Yong, or after a consultation with nothing dispensed, a handover is refused (`wrong_stage`). A **referral** is something else: the letter sending a patient to an outside specialist or hospital, decided only by the GP in the consultation.
- **Replies follow the access-level reply levels** (`~/.claude/rules/access-level-chat-replies.md`): read only, one sentence opening "Here it is:"; read and follow up, at most two short sentences, no "pending"; a handover sent, "Sent to <name>, <job title>."; no authority, "I'm sorry, you can't ... Only <name>, <job title>, can ..."; no access, "I'm sorry, ... isn't open to you. Only ..., can access it."; the decider's answer, "OK. ...". The receiver reads the code-written two-sentence notice first. Fixed outcomes are written in code (`next_step.say`) and shown as they are. Never "he" or "she"; never name the signed-in person. Code adds the Basis line.
- **Money in sen, times in Unix seconds** in the data and the back end. PostToolUse converts to RM and Malaysia time; tool inputs take RM (`amount_rm`, `tendered_rm`, `counted_cash_rm`) and never a price or a total.

## Build steps, in order
```
npm install
python build_policies.py                       # resources/ and policies.html, after a change in sources/
python generate_data.py                        # data/
python benchmark/build_cases.py                # benchmark/cases.json and Answer Key.html
node benchmark/test_tools.js                   # no key
node benchmark/test_mcp.mjs                    # no key
node benchmark/run_benchmark.js --sample       # B3-PH, C1-PH, C6-FD, D1 -> sample.json
node benchmark/run_benchmark.js --only C1-PH,F3 --out rerun-check
node benchmark/run_benchmark.js                # full run -> results.json
node build_desk_preview.mjs                    # desk-preview.html, desk-layout1.html, clinic-desk.html
python benchmark/build_sample_page.py          # benchmark/Sample Questions.html
```
The benchmark reads `ANTHROPIC_API_KEY`, or the line in `~/.env`. Other flags: `--group own_job|unauthorised|handover|workflow|failure`, `--parallel 5`, `--model`, `--rescore` (rescore the saved `<out>.json` from `runs/` with no model call).

## After a change to code or prompt
1. Run the no-key tests, `node benchmark/test_tools.js` and `node benchmark/test_mcp.mjs`. All must pass before any paid run.
2. Rerun the affected runs with `--only <run IDs> --out <name>`.
3. Then one full run. Hard-limit breaches must stay 0. Read the replies against the reply levels even after a perfect score.
4. Rebuild the pages (`node build_desk_preview.mjs`, `python benchmark/build_sample_page.py`) and check `clinic-desk.html`, Replay and Live, wide and narrow.

Do not edit `data/`, `resources/`, `policies.html`, `benchmark/cases.json`, `benchmark/Answer Key.html`, `benchmark/Sample Questions.html` or the three desk pages by hand; they are build outputs.
